# Independent review of the revision 6 evidence standard

Revise the standard before adopting it on #48. The draft treats live observations as general guarantees in several rows, and the proof line misses a replay defect that can repeat an external effect before any operator-visible failure. The owner already selected a proof fallback for concurrent timing in #48. The new decision is how to express that obligation in the standard.

A comment number refers to #48 unless specified otherwise. Fixture verdicts below come from the saved outputs and, where needed, the checkers or handler source. ## Findings and closure evidence

1. **Critical. The process-survives guarantee covers a case the owner explicitly accepted would lose the record**. Rows 15 and 16 say every executed run's outcome is journaled while the process survives. The same process can survive an SDK abort timeout while the attempt ends before recording that run. R5 has a first attempt without the result and a second attempt that records a terminal abort. R1 keeps the run's record in its tested shapes but fails its combined gate because delivery stalls. R3 deadlocks with the delivery barrier. R3s establishes the sibling's result by the failed attempt, with two cases where `aJournaledBeforeReject=false`. Neither the failed variants nor the revised predicate prove the unconditional guarantee. State the success, SDK-owned cut, crash, terminal abort and retry cases separately. Define the required ordering between closure settlement, result proposal, server acknowledgement or persistence, and the attempt-ending failure. Add a scoped statement and controls at those boundaries. Keep a duplicate-then-success mutant for re-abort, and prove re-abort ordering given the conditions under which the lost race or deadline is reconstructed. `spike/rev6/runs/run-out.txt:38–57,66–93`; `spike/rev6/rerun/run-out.txt:18–30`; comments 7121677014, 7132209348.

2. **Critical. A43 does not establish the proposed compensation identity or the attach recovery policy**. Two loop iterations, or two parent invocations, can reach the same source site with different compensation payloads. Under the same scope, service, object key, handler and supplied idempotency key, A39 says the second payload aliases the first. A43 gets two distinct keys from the driver. Its attach code tries again after a rejection and caps the loop at four, so the output does not establish tolerance of arbitrary repeated cancels. It also does not show a crash between issuing the send, obtaining its ID and attaching. Define the identity across dynamic call occurrence, parent and replay, and qualify any exactly-once claim by retention, child retry or crash, and the kill boundary. Specify which rejections re-attach, when retry continues, and what terminal child failure looks like. Use same-site, cross-parent, same-key/different-payload, repeated-cancel and crash/replay fixtures with controls. `spike/rev6/idem/handlers.mjs:174–201`; `fixtures.mjs:403–421` in that directory; `run-out-a43.txt:16–29,38–47,58–64`; comments 7120729029, 7121147686, 7121240220.

3. **High. Journal order needs a reachability argument and a defined journal comparison**. F1 and F9 show run-result order in the tested cases. F2 shows that two ready sleeps can win in array order after a subset wait. F19 shows that an SDK failure may end an attempt across concurrent runs. Rows 2, 3 and 11 do not specify whether sample waits, attach recovery and cancellation can produce analogous ready sets. F20 distinguishes journal validation from an executor's stronger claim: changed race membership and reordered awakeables can replay without a mismatch. State which entries are observable, including call IDs, signals, samples and SDK-generated commands, and define accepted membership and buffered results at each step. Prove the reachability condition or specify the actual tie order. Add mixed-operation and subset-wait controls, with a sample pending during cancel and attempt cuts. `spike/rev6/order/run-out.txt:102–127,168–175,211–214`; `spike/rev6/cancel/run-out.txt:588–690`; #32 and #35.

4. **High. The terminal conversion gate misses an unrelated transient failure after abort**. In R4 the actual predicate is `convert && controller.signal.aborted`. A closure can ignore that signal, then receive an unrelated retryable failure while the flag is true. The wrapper will record a terminal error even if the external action never happened. R4's ignoring closure succeeds, so neither negative control distinguishes the bad conversion. Define what constitutes attributable cancellation under each supported API, what happens if causation is unknown, and what a terminal outcome says about the external action. Include a concurrent unrelated rejection, an abort that follows an already-committed write, and a deadline-driven abort. `spike/rev6/runs/abort.mjs:19–41,59–74`; `run-out.txt:94–103` in that directory; SDK 1.18.4 `spike/node_modules/@restatedev/restate-sdk/dist/context_impl.js:245–272`.

5. **High. The draft needs claim scopes, proof coverage and acceptance criteria for evidence**. The register, external axioms, test obligations and theorems have different jobs. Record each claim in observable terms, with allowed programs, runtime versions, attempt boundaries and source preconditions. For each dependency, give the fixture and the failing control for that scope, or mark the gap. For each theorem, inventory permitted axioms across exported definitions as well as theorems and map each runtime premise to evidence. Use #30's witnesses for semantic omissions and #36's module-level `False` mutant to challenge the gate. For the bounded oracle, publish its grammar, bounds, project-floor coverage and explicit exclusions before running it. The report should give coverage by relevant boundary, including mixed operation kinds, attempts, queued versus executing runs, cancellation during samples and uninterruptible cleanup. A passing isolated fixture is useful evidence for its own scope. A proof over inputs that cannot express an approved behavior leaves that behavior unverified.

6. **Medium. The second warning is checked against a wide interval and uses a proxy for server activity**. The saved run supports a boundary between probes due at 3.5 s and 7 s. It distinguishes the last-send policy in that trace. The checker accepts any warning in that interval even if 3 s have not elapsed since the last delivery. The handler moves its timer on selected race deliveries and at issue, so it does not observe every exchange in both directions. The fixture's warning callback can also fire before abort, discard it, then lack a new exchange to rearm it. Define the warning against an observable local condition or get and test a verifiable server-side inactivity marker. Include a premature-warning mutant within the bracket, abort after the nominal deadline, replay before or after the grace period, and closure settlement versus result delivery. `spike/rev6/rerun/run-out-1.txt:31–39`; `run-out.txt:31–39`, `warn.mjs:40–58,76–98` and `check-r6.mjs:24–59` in that directory.

7. **Medium. The time decision is wider than the proposal's stated exception**. The owner already described new proof work for overlap and approved a fallback that proves single-operation timing. A single sample per turn affects journal shape and cancellation during pending samples even for a consumer that never branches on the numeric time. A sleep chain changes both issued commands and which prefix is credited at cancellation. The maximum of samples is also only one part of the old rule, `max(L + floor, sample)`. Distinguish the simple max calculation from end-to-end time, cancellation and replay claims. Keep the owner's proof fallback explicit and add requirements for backwards samples, indistinguishable timing traces and cancel between timer and sample. `verification/proofs/Scheduling/Model.v:178–183`; `Statements.v:195–257` and `TimeRule.v:1–8` in that directory; #32 and #35; comment 7121677014 and #48's body.

## Restrictions, boundary checks and known weaknesses

| Draft assumption or restriction | Boundary that challenges it |
|---|---|
| One race over pending operations lets the model assume journal order | An intervening sample wait can make multiple members ready. F2 distinguishes array priority from journal order in the subset case. The revision still needs a reachability check. |
| One derived key per site is enough | Two dynamic visits to the same site can have different payloads. A39 and A43 distinguish a scope assumption from a verified key algorithm. |
| Process survival implies journal persistence for executed runs | An SDK abort timeout ends the attempt while its closure winds down. R5 distinguishes process survival from attempt survival. |
| A later retry pause counts as observability | A retry can repeat work and then return success with one retained result. R5 shows repeated work before the harness intervenes. |
| A warning between two probes establishes the exact timeout | The saved checker accepts a warning at the last on-time delivery. The separate deadline claim requires tighter evidence. |
